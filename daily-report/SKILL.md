# 日报撰写指南 (Daily Report)

本技能用于帮助用户撰写工作日报。日报包含「进展」与「计划」两大板块，每个任务都必须对应到具体的项目名。

## 生效条件 / Invocation Conditions

当用户消息中出现以下任一关键词时自动触发（无需用户显式指定技能名）：

- 写日报、写份日报、帮我写日报
- 生成日报、生成一份日报、整理日报、输出日报
- 日报、工作日报、今日日报、daily report、daily summary
- 提供了当天的工作内容 / 任务记录 / 会议纪要 / 聊天记录等素材并要求整理

## 输出格式（优先遵守）

默认输出**纯文本直粘版**，面向「企业微信 Windows 版内置邮件」的富文本编辑器。该编辑器**不解析 Markdown**：粘入 Markdown 源码时 `**` 等标记会原样显示。因此日报正文必须满足：

- **不得出现任何 Markdown 标记**：不用 `**粗体**`、`#` 标题、`-` / `*` 列表、反引号、引用符、表格等。
- **不得出现 HTML 标签或内联样式**（`<font>`、`<div>`、`<br>`、`style="..."`），也不写入任何字号 / 字体控制。
- **标题行写「进展」「计划」两行纯文本**，各自独占一行；标题与下方正文之间空一行。标题不预置加粗，用户粘贴到邮件后自行 `Ctrl+B` 加粗即可。
- **缩进用行首两个全角空格**（`　　`，U+3000），不用 ASCII 空格或 Tab（粘贴到富文本编辑器可能被折叠）。
- 版式全部靠**空行 + 换行 + 全角空格**实现，除此以外不加任何装饰。
- 在回复中**用代码块包裹整份日报**，避免 Markdown 渲染吞掉换行、便于整段复制；代码块内的字符即最终要粘贴的内容。
- 仅当用户**明确要求** Markdown 或 HTML 版本时，才改用对应格式输出。

## 写作要求

日报内容包含两个板块：

1. **进展**：罗列当天的工作任务。**每个任务必须对应到具体的项目名**，并包含该任务今天的进度；预计完成时间如有需要可注明（可选）。
2. **计划**：罗列未完成的任务及第二天的计划安排。

要点：

- 项目名放在每条任务的开头（如 `FY6718`），后跟任务主题。
- 任务状态需标注，如「进行中」「已完成」等。
- 具体进度细节写在对应任务下方，**必须另起一行**，一条一条列清楚，不使用大段连排文字。
- **细节行不加任何圆点 / 项目符号**（不用 `-`、`•`、`*`、缩进圆点等），改用**行首两个全角空格（`　　`）**实现缩进。
- **同一任务内部只换行、不加空行**：任务行与其细节行之间、相邻细节行之间都**不留空行**，直接换行即可（粘贴到企业微信邮件后换行会原样保留）。
- **不同任务之间空一行**：相邻的序号任务（如第 1 条与第 2 条）之间留一个空行，让条目边界清晰。
- **若某条内容较多，可再拆分为多行**，每行长度约一两句话。
- 若同一项目下有多项子任务，按子任务逐条拆分列出（如 BUG 修改中不同 BUG / 不同需求分别列出）。
- 语言简洁、客观，直接陈述进度与事实，避免空话套话。
- **对用户提供的内容做简单润色并适度扩写**：理顺语句、补齐惯用表达（如版本构建发布流程、问题处理状态等），使日报读起来完整流畅；扩写应基于用户素材合理展开，不虚构事实、不夸大进度。
- **内容不明确时先提问再动笔**：项目名缺失、任务归属不清、状态不明、扩写所需背景不足等情况下，先向用户提出澄清问题，待用户明确后再生成日报，而不是猜测硬写。

## 日报格式模板

```
进展

1. <项目名> <任务主题>。<状态>
　　<该任务的进度细节，独占一行、行首两个全角空格缩进、不加圆点；内容较多时每行约一两句话，可拆多行>
　　<多条进度细节逐条罗列>

2. <项目名> <任务主题>。<状态>
　　<进度细节>

计划

1. <项目名> <任务主题>。
　　<计划细节>

2. <项目名> <任务主题>。
　　<计划细节>
```

> 注：整份日报在回复中用代码块包裹输出；任务行与细节行之间不加空行，不同任务之间空一行；细节行行首两个全角空格缩进，不加任何圆点，也不加任何 Markdown / HTML 标记。

### 参考示例

```

　　心率等测试项按需求调整测试时长和周期，已完成。

　　日历应用新需求待开发。
　　计时器显示BUG待修改。

3. FY6718 支持客户关于GPS定位精度的问题。
　　已与客户沟通协议原理，待客户抓LOG后进一步确认。

计划

1. FY6718 处理禅道问题。
　　梳理禅道遗留问题清单，按优先级排期处理。

2. FY6718 生产测试需求开发。
　　完成测试时长与周期调整，提交测试验证。
```

## 输出约定

- 默认输出**纯文本直粘版**（不带任何 Markdown / HTML 标记），并在回复中用**代码块**包裹，便于整段复制到企业微信邮件正文。
- 标题「进展」「计划」不加粗、不加装饰；若用户希望加粗，提示其在邮件客户端选中后 `Ctrl+B`。
- 若用户明确要求 Markdown 或 HTML 版本，则改按该格式输出（Markdown 版：`**进展**` / `**计划**` 粗体标题，标题与正文间空一行，任务内每行末尾加 `<br>` 硬换行、不加空行，不同任务之间空一行）。
- 输出直接呈现在回复中，除非用户明确要求写入文件 / 追加到指定文档。
- 生成后可主动询问用户是否需要调整措辞、增删条目或补充计划。

### 邮件正文格式

邮件正文按 Markdown 渲染，与纯文本直粘版略有差异：

- 「进展」「计划」写成加粗标题 `**进展**` / `**计划**`，标题与正文之间空一行。
- **同一任务内部的换行，必须在每行末尾加 `<br>`**（任务行与其细节行之间、相邻细节行之间都要），否则 Markdown 会把同一条目内的多行合并成一段。
  **注意：行尾两个空格（Markdown 硬换行）在企业微信邮件里不生效，切勿使用。** 实测有效的三种写法：行尾 `<br>`、行尾反斜杠 `\`、行间空一行；其中 `<br>` 最稳妥且不额外增加行距，**默认用 `<br>`**。
- 不同任务之间空一行；细节行仍用行首两个全角空格（`　　`）缩进、不加圆点。

### wecom-cli 使用规则

1. **先读技能文档**：执行任何 `wecom-cli` 命令前，先读取 `wecomcli-shared`（公共前置检查）与 `wecomcli-email`（发信流程）技能文档，按其规范执行。
2. **版本检查**：`wecom-cli --version` 需不低于 `1.2.1`。PATH 中的内置版本可能偏低（如 `1.1.0`）；若低于要求，**改用 npm 全局版本**，用全路径调用：
   `C:\Users\zhang\AppData\Local\Programs\nodejs\wecom-cli.cmd`
   不要为此重新安装。
3. **授权检查**：`wecom-cli auth show --status` 输出 `authorized` 才可发信；未授权时按 `wecomcli-shared` 走初始化流程。
4. **中文编码**：调用前将 `$OutputEncoding` 与 `[Console]::OutputEncoding` 设为 UTF-8，避免中文标题乱码。
5. **正文走文件**：把 Markdown 正文写入临时文件（如 `%TEMP%\wecom_mail_body_<唯一后缀>.md`），命令里用 `file_path` 指向该文件、`content_type` 填 `markdown`。
6. **收件人无需查通讯录**：收件人 / 抄送均为完整邮箱地址，直接填入 `to.emails` / `cc.emails`。
7. **先预览、待确认**：发送前先在对话中展示主题、收件人 / 抄送与正文预览；**默认等待用户确认后再发送**，除非用户明确表示直接发送。
8. **发送后**：向用户确认「邮件已成功发送」并展示收件人与主题；不得外露 `mail_id` 等内部 ID。发送完成可清理临时正文文件。

调用示例（PowerShell）：

```powershell
$OutputEncoding = [System.Text.Encoding]::UTF8; [Console]::OutputEncoding = [System.Text.Encoding]::UTF8; chcp 65001 | Out-Null
& "C:\Users\zhang\AppData\Local\Programs\nodejs\wecom-cli.cmd" mail send --json '{
  "to": { "emails": ["peter@deepailink.com","mengzitianyu@deepailink.com","liuxun@deepailink.com","changjiawei@deepailink.com","lvhao@deepailink.com","lixing@deepailink.com"] },

  "subject": "日报 Leon 10月13日",
  "file_path": "%TEMP%\\wecom_mail_body_daily.md",

```
